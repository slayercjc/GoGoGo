# 发布幻位新版

应用只读取 slayercjc/GoGoGo 的最新正式 Release。无需服务器，不要把 GitHub Token 放入 APK。

## 先测试，再发布

1. 在 `android16-baidu` 分支修改 `app/build.gradle`：`versionName` 改为新版本，例如 `1.2`；`versionCode` 必须比之前大，例如从 `1123` 改为 `1124`。请勿把内部版本码重置为 1。
2. 提交代码。提交信息含 `[signed-apk]` 时，GitHub Actions 自动编译签名版；也可在 Actions 的 **Android 16 build → Run workflow** 中选择 `android16-baidu` 和 `signed-apk`（如果默认分支没有此工作流入口，可使用提交方式触发）。
3. 等待绿色成功，下载 `HuanWei-signed` 压缩包，解压得到 APK、`update.json`、SHA256SUMS.txt 和校验报告。先在手机上覆盖安装测试。
4. 打开仓库 **Releases → Draft a new release**。创建标签，例如 `v1.2`，**Target 选择 android16-baidu**，标题填写“幻位 1.2”，写好更新内容。
5. 将同一次构建中的 **APK、update.json、SHA256SUMS.txt** 一起上传。不要修改其中的文件名或只上传 APK。
6. 正式发布时不要勾选 **Set as a pre-release**，将它设为最新版本，点击 **Publish release**。草稿和预发布不会被正常更新接口采用。

这条网页发布流程最直观，可先编辑草稿、最后发布。创建或发布 Release 不等于对手机上已经安装的旧 APK 增加更新能力：幻位 1.0 仍是打开网页，需要先手动安装具备更新功能的 1.1。

## 使用标签自动发布（可选）

此分支的工作流也支持推送 `v*` 标签：在版本修改和测试通过后，把与 `versionName` 完全一致的标签（如 `v1.2`）推送到本分支提交。工作流会重新编译、验证签名、生成 update.json，再自动创建 Release 并上传文件。

不要同时对同一版本混用网页上传和标签自动发布。标签必须指向包含新版代码和此工作流的提交；不要把标签建在仍保存上游代码的 master 上。自动发布失败时可使用已生成的构建产物走上面的网页流程。

## 手机端行为

- 默认开启应用时检查，每天最多一次；“检查更新”可随时手动检查。
- 默认先显示版本说明，用户点击下载。可在设置中开启“仅 Wi-Fi 自动下载”。
- 系统下载管理器负责进度、网络恢复和通知；关闭页面不会取消下载。再次点击检查更新可查看状态或取消任务。
- 下载后校验文件长度、SHA-256、包名、内部版本号、显示版本和安装包签名。失败则拒绝安装并清理任务。
- 下载期间离开应用时不会强行弹出安装页面。回到应用后继续校验和安装提示。
- 第一次需要授予“允许安装未知应用”；安装由 Android / HyperOS 确认。安装会中断正在运行的模拟定位服务。
- 必须持续使用同一个 `gogogo-release.jks`。不要丢失或公开密钥、密码以及 GitHub Secrets。
- GitHub 网络不可达、限流、没有正式 Release、缺少 update.json 时会给出提示，可打开发布页手动下载。

## 测试清单

先保留旧版 APK，再用更高内部版本发布新版：测试发现新版、取消下载、Wi-Fi 等待、下载完成后重开应用、拒绝安装权限后重试、覆盖安装后不再提示旧更新。错误签名、错误 SHA-256 和错误包名只在测试仓库或本地测试环境验证，不要发布给正式用户。
